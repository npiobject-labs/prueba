## El riesgo de D8 ha cambiado de naturaleza

El plan anotaba en F1 un riesgo abierto: sin `TOKEN_API`, la API es pública y
cualquiera con la URL puede escribir. Hasta hoy eso significaba notas basura en
una base de datos personal, molesto y reparable. Desde F2 significa otra cosa:
cada `POST /notas` llama a un modelo y **gasta dinero real** de la clave de
OpenRouter. El tope de la aplicación en el servicio acota el daño a 2 $ por día
y 25 llamadas por minuto, que es justo para lo que sirven los topes, pero el
riesgo ya no es de higiene sino de factura. El secreto `TOKEN_API` deja de ser
«si molesta, se adelanta» y pasa a ser lo primero.

## Lo que enseñó la primera nota real

La verificación del despliegue creó una nota de verdad y el modelo la tituló
bien: «Pedir presupuesto para revisión y neumáticos del coche». Las etiquetas,
en cambio, salieron `["coche","nota","personal","presupuesto"]`. Dos de las
cuatro no distinguen nada en una aplicación de notas personales, y el defecto
se habría agravado solo: a cada nota nueva se le pasan las etiquetas existentes
para que reutilice antes de inventar, así que «nota» y «personal» se habrían
propagado a todo el vocabulario. Se corrigió por los dos lados: el prompt las
prohíbe con nombre y apellidos, y `limpiar` las descarta por si el modelo
insiste, que es donde no hay margen de error. La lección es que un vocabulario
que se realimenta necesita un filtro, no solo una instrucción: basta con que el
modelo falle una vez para que el ruido entre y ya no salga.
