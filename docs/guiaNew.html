Método DesdeMovil · plantilla npiobject-labs/DesdeMovil

Crear y desarrollar un proyecto desde el móvil, con el PC apagado

Todo lo que hay que hacer, en orden, para arrancar un proyecto nuevo desde la plantilla y trabajarlo desde la app de Claude en el móvil. El código y la documentación viven en GitHub; GitHub Pages publica los mocks; Fly.io y Google Drive son opcionales. El PC solo entra al final, para aterrizar una copia.

Versión 3 (guiaNew) · 6 sep 2026 · plantilla con portado de los proyectos hijos Organización GitHub: npiobject-labs Las casillas se guardan en este navegador
Escríbelo y todas las direcciones y textos de esta guía se rellenan solos. Sin espacios ni tildes; es el nombre que tendrá el repositorio.
Una sola vez

Cuentas conectadas

Ya está hecho en tu cuenta. Está aquí para que la guía sea completa y para revisarlo si algo deja de funcionar.

GitHub conectado a Claude Code en la nube

Dónde: claude.ai/code (en la app, el icono </> del panel lateral; en el móvil, pestaña Code).

La primera vez pide "Sign in with GitHub". Autoriza con tu cuenta personal, la que es miembro de la organización npiobject-labs. A partir de ahí, el selector "Seleccionar repositorio…" bajo la caja de texto lista los repos de la organización.

Cómo saber que está bien: al abrir claude.ai/code ves "Seleccionar repositorio…" y al pulsarlo aparece npiobject-labs/DesdeMovil.

Fly.io (solo si algún proyecto va a tener backend)

Dónde: fly.io/dashboard.

No hay nada que preparar por proyecto. FLY_API_TOKEN es un secreto de la organización npiobject-labs y lo heredan todos sus repos públicos: ya no se crea un token de Fly por proyecto.

Conector de Google Drive en Claude (solo si quieres copias en Drive)

Las sesiones de Code ya han demostrado tener el conector de Drive disponible. No requiere nada del PC.

Ojo: el conector escribe en carpetas normales de Mi unidad. Un "Proyecto" de Drive (la función nueva de Drive con ese nombre) no sirve: no admite ficheros del conector.

Por proyecto · 2 pasos

Crear el proyecto

Cinco minutos desde el móvil. Solo estos dos pasos exigen tu mano; el resto lo hace la sesión de Code.

1 · Generar el repositorio desde la plantilla

Dónde: github.com/new?template_name=DesdeMovil&template_owner=npiobject-labs (con sesión iniciada en GitHub). En Owner elige npiobject-labs, no tu cuenta personal, y déjalo Public: de ahí hereda el repo el secreto FLY_API_TOKEN de la organización. En el plan Free, un repo privado no recibe los secretos de la organización.

Ese enlace abre el formulario de "Create a new repository" con la plantilla ya elegida. Rellena solo Repository name con MiProyecto, déjalo Public (Pages gratuito exige repo público) y pulsa Create repository.

Si en la portada de npiobject-labs/DesdeMovil no ves el botón verde "Use this template", es que no has iniciado sesión en GitHub en ese navegador. El enlace de arriba evita buscar el botón.

Qué debes ver: el repo nuevo en github.com/npiobject-labs/MiProyecto con los mismos ficheros que la plantilla (ARRANQUE.md, CLAUDE.md, docs/, app/, tools/). Al cabo de un minuto, el workflow Inicializar plantilla deja el repo entero con tu nombre: sustituye "DesdeMovil" y el owner en README.md, CLAUDE.md, ARRANQUE.md, tools/*.ps1, docs/*.html y app/src/main.rs; renombra el paquete del backend (<slug>-backend en app/Cargo.toml, Cargo.lock y Dockerfile); fija el prefijo de los builds con las iniciales del proyecto (CasaVerde → CV-B1-…); rellena la tabla Parámetros de CLAUDE.md con el id de Drive vacío; aparta la documentación heredada de la plantilla a docs/plantilla/ (solo lectura) y deja docs/planificacion/ limpia para tu proyecto. Al final hace un grep de todo lo que huela a plantilla y falla el run si encuentra restos: ese grep es el checklist, no hace falta revisar ficheros a mano. Después borra el marcador .plantilla-pendiente, se deshabilita a sí mismo por la API (no puede borrarse: GITHUB_TOKEN no tiene permiso para tocar .github/workflows/) y relanza Pages.

El primer run de Pages sale en rojo, y es normal. "Use this template" dispara el workflow de Pages con el commit inicial, antes de que hayas hecho el paso 2. Ese run falla con Create Pages site failed… Resource not accessible by integration. No lo arregles: el workflow de inicialización relanza Pages al terminar, ya con el origen correcto. (El de Fly, en cambio, despliega: el token le llega heredado de la organización.)

Si en Actions no aparece ese run, lánzalo a mano: Actions → Inicializar plantilla → Run workflow. También lo hará la sesión de Code del paso 3 si lo encuentra pendiente.

2 · Activar GitHub Pages con origen "GitHub Actions"

Dónde: github.com/npiobject-labs/MiProyecto/settings/pages

En Build and deployment → Source, despliega el menú y elige GitHub Actions. No hay botón de guardar: al elegirlo queda hecho.

Este es el error más fácil de cometer. El menú viene de fábrica en "Deploy from a branch". Si lo dejas así, GitHub publica la raíz del repo con su constructor antiguo: tendrás un enlace que funciona pero muestra el README, no el mock de docs/. Si te pasa, vuelve aquí y cambia el origen; la siguiente publicación lo corrige.

Qué debes ver: bajo "Source" pone "GitHub Actions" y desaparece el selector de rama.

Cómo saber si se te olvidó: en la pestaña Actions aparece, tras cada push, un run llamado pages build and deployment con un paso Build with Jekyll. Ese constructor solo existe en el modo antiguo; con el origen en "GitHub Actions" no vuelve a aparecer.

3 · Primera sesión de Code: comprobar que todo responde

Dónde: app de Claude → pestaña Code → "Seleccionar repositorio…" → npiobject-labs/MiProyecto, rama main.

Pega esta instrucción tal cual:

Verifica que el proyecto quedó inicializado y que Pages responde. Si sigue existiendo .plantilla-pendiente, lanza el workflow "Inicializar plantilla" y espera a que termine. Dime SHA, URL de Pages y número de build.

Qué debes ver: la sesión responde con la URL npiobject-labs.github.io/MiProyecto/ y, al abrirla en el móvil, la página dice "MiProyecto · mock 0" con un build que empieza por las iniciales de tu proyecto. Si muestra un README, revisa el paso 2. En el repo, docs/planificacion/ debe estar vacía salvo su README.md, y lo heredado de la plantilla en docs/plantilla/.

En Actions verás también el workflow Desplegar backend en Fly.io terminando en verde con el aviso "Fly no configurado". Es lo esperado: Fly es opcional y se activa en la fase de más abajo cuando haga falta.

Cada día

Desarrollar desde el móvil

El ciclo de trabajo normal. El PC no interviene en ninguna vuelta.

Tú, en el móvilEscribes la instrucción en la sesión de Code del proyecto.
Sesión de CodeEdita, prueba en su sandbox, hace commit y push a main.
GitHub ActionsPublica docs/ en Pages y, si Fly está activo, despliega app/. Verifica las URLs.
Sesión de CodeLee el resultado del workflow y solo entonces te avisa: SHA, URL, build.
Tú, en el móvilAbres la URL, pruebas, y pides el siguiente cambio.

Cómo pedir las cosas

Una instrucción por objetivo, concreta. La sesión ya sabe las reglas por CLAUDE.md: mocks en docs/, cada uno con su número de build, documentación en docs/planificacion/, verificación antes de avisar. Ejemplos que funcionan bien:

Añade a docs/index.html una pantalla de inicio de sesión (usuario, contraseña, botón). Sube el build a 002, publica y dime cuándo puedo verlo.
Resume en docs/planificacion/decisiones.md las decisiones de diseño tomadas hasta hoy, con fecha, y haz push.

Cuándo fiarte de "ya puedes probarlo"

Solo cuando el aviso trae el SHA del commit y el número de build, y el workflow está en verde. Puedes comprobarlo tú en la pestaña Actions del repo: el último run de "Deploy docs to GitHub Pages" debe tener la marca verde.

La sesión no puede abrir tu web desde su sandbox (bloquea *.github.io y Fly). Por eso quien verifica es el workflow, y la sesión solo lee su resultado. Si una sesión dice "no puedo acceder a la URL", es normal; lo que importa es el run.

Al terminar cada sesión

Pide el cierre: la sesión escribe un resumen de cinco líneas (qué cambió, SHA, URL, estado de Drive, qué falta) en docs/planificacion/sesiones/ y una entrada nueva en docs/bitacora/AAAAMMDD-HHMM.json. El resumen es lo que leerá la siguiente sesión para continuar, así que no lo saltes.

La entrada aparece en la bitácora del proyecto (npiobject-labs.github.io/MiProyecto/bitacora.html): sesiones en orden inverso, con buscador, lo que se pidió, qué cambió y enlaces al commit, al run y al mock de ese día. Es pública y no necesita cuenta.

Cierra la sesión: resumen de 5 líneas en docs/planificacion/sesiones/ y entrada
nueva en docs/bitacora/AAAAMMDD-HHMM.json con objetivo, los prompts de esta
sesión, qué cambió, SHA, run de Actions, mock archivado y URL de Fly si aplica.
Push, verifica que Pages queda en verde, y sube la copia a Drive.
Opcional · cuando haga falta

Fly.io a mitad de proyecto

El día que el proyecto necesita un servidor propio (API, base de datos, algo que no cabe en una página estática). Nada de lo hecho hasta entonces cambia: el repo ya trae app/ con un servicio Rust mínimo y el workflow de despliegue, con el token ya en la mano.

1 · Comprobar que no hay nada que activar

Dónde: github.com/npiobject-labs/MiProyecto/settings/secrets/actions

FLY_API_TOKEN es un secreto de organización de npiobject-labs: lo heredan todos sus repos públicos. No crees ningún token de Fly ni ningún secreto de repositorio; ya no hace falta.

El repo tiene que ser público. En el plan Free de GitHub los secretos de organización no llegan a los repos privados: ahí deploy.yml terminaría en verde con el aviso "Fly no configurado" y no desplegaría nada.

Qué debes ver: en esa pantalla, FLY_API_TOKEN bajo Organization secrets. Si solo lo ves bajo Repository secrets, es un resto de la forma antigua y puedes borrarlo.

2 · Lanzar el primer despliegue

El siguiente push que toque app/ despliega solo. Para forzarlo, dos formas: desde la sesión de Code,

Lanza el workflow de despliegue a Fly sobre main, espera al run, verifica por API que termina en verde y dime la URL de la app y la respuesta de /salud.

O a mano: pestaña Actions del repo → Desplegar backend en Fly.io → Run workflow sobre main.

El nombre de la app lo deriva el workflow como <repo>-<owner> en minúsculas, con todo lo que no sea letra, número o guion convertido en guion y recortado a 30 caracteres: para este proyecto, miproyecto-npiobject-labs. Si prefieres otro, crea antes la variable de repositorio FLY_APP (misma pantalla que los secretos, pestaña Variables, esta sí del repo) y anótalo en la fila "App de Fly.io" de la tabla Parámetros de CLAUDE.md. Los nombres son únicos en todo Fly.io, no solo en tu cuenta: por eso el derivado lleva el owner de sufijo. Si aun así el nombre ya está cogido, la creación no protesta y el fallo aparece más tarde, en el paso de despliegue, con un mensaje que no apunta a la causa; la salida es definir FLY_APP con otro nombre y relanzar.

El primer despliegue tarda varios minutos porque compila Rust desde cero. Los siguientes van rápidos. A partir de aquí, cada push que toque app/ despliega solo.

Qué debes ver: https://<app>.fly.dev/salud responde {"ok":true,"build":"<SHA del commit>"}. El resumen del run en Actions muestra el nombre exacto de la app y la URL.

Opcional

Copias de la documentación en Google Drive

Si quieres hojear la documentación desde la app de Drive. Es un espejo: nada de lo que hay en Drive es origen de nada.

Crear la carpeta y anotar su id

Dónde: Mi unidad → Nueva carpeta → nómbrala MiProyecto. Ábrela: el id es el último tramo de la dirección, tras /folders/.

Luego, en la sesión de Code:

Pon este id en la fila "Carpeta de Drive (id)" de la tabla Parámetros de CLAUDE.md y haz push: <PEGA-AQUÍ-EL-ID>. A partir de ahora, al cerrar cada sesión sube copias de docs/planificacion/ a esa carpeta.

Regla: en Drive nunca se borra ni se renombra nada, ni tú ni la sesión. Si hay que sustituir un documento, se sube con sufijo -v2. Un borrado en Drive ya nos costó un informe.

Cuando quieras · PC encendido

Aterrizar el proyecto en el PC

Una copia de consulta en Windows 11. Repetible cuantas veces quieras; siempre sobrescribe lo local con lo que hay en GitHub. Nunca se edita en el PC.

Primera vez: una línea en PowerShell

Descarga el script de aterrizaje desde el repo y lo ejecuta. Deja el proyecto en C:\Users\<tú>\C - Desarrollo\MiProyecto\repo.

& ([scriptblock]::Create((irm https://raw.githubusercontent.com/npiobject-labs/DesdeMovil/main/tools/aterrizar.ps1))) -Proyecto MiProyecto

Si PowerShell bloquea la ejecución: antepón powershell -ExecutionPolicy Bypass -Command y la línea entre comillas. Requiere git instalado.

La carpeta repo\ debe estar vacía o no existir la primera vez. Si tiene cualquier fichero (un script guardado a mano, por ejemplo), el aterrizaje lo dice y se detiene sin tocar nada: vacíala y repite. No guardes nada dentro de repo\: cada aterrizaje borra lo que no esté en GitHub.

Siguientes veces y comprobación

Desde la copia local: tools\aterrizar.ps1 vuelve a dejarla igual que main. tools\estado.ps1 dice AL DIA o DESACTUALIZADO sin tocar nada.

Prueba de confianza: borra un fichero cualquiera de repo\, ejecuta aterrizar.ps1 y debe reaparecer. Ejecútalo dos veces seguidas y la segunda no debe cambiar nada. [SUPUESTO] los scripts de PowerShell no se han llegado a ejecutar nunca: no hay pwsh en el sandbox de las sesiones, así que esta es la comprobación pendiente en el primer PC donde se usen.

La copia viva de esta guía está en docs/guiaNew.html del repo y publicada en Pages. Si la guardas en el PC, fuera de repo\: aterrizar.ps1 borra todo lo que sobra dentro de repo\.

Cuando un proyecto sobra

Eliminar un proyecto sin dejar restos

Un proyecto toca cuatro herramientas. Bórralo en este orden y no quedará nada colgando ni consumiendo cuota.

Con el repo aterrizado en el PC, tools\eliminar.ps1 hace los tres primeros pasos: pwsh -File tools\eliminar.ps1 enseña el plan sin tocar nada, y -Confirmar lo ejecuta pidiéndote el nombre del proyecto. Necesita flyctl y gh; lo que falte lo deja anotado como pendiente. Drive y las sesiones siguen siendo a mano.

1 · Fly.io: la app

Dónde: fly.io/dashboard → la app (miproyecto-npiobject-labs o el nombre que pusieras en FLY_APP) → Settings → Delete app. Confirma escribiendo el nombre.

Al borrar la app se liberan sus máquinas, volúmenes e IPs; comprueba en el dashboard que la lista de apps ya no la muestra. No se revoca ningún token: FLY_API_TOKEN es de la organización y lo usan los demás proyectos.

Si nunca activaste Fly en este proyecto, no hay nada que borrar aquí.

2 · GitHub: el repositorio

Dónde: github.com/npiobject-labs/MiProyecto/settings → al final de la página, Danger Zone → Delete this repository.

Con el repo se van su sitio de Pages, sus variables y sus workflows. El secreto FLY_API_TOKEN no: vive en la organización y sigue ahí para los demás proyectos. Por eso Fly va antes: una vez borrado el repo ya no tienes a mano el nombre de la app.

3 · Google Drive: la carpeta de copias

Dónde: Mi unidad → carpeta MiProyecto → Mover a la papelera. Y vacía la papelera si quieres que desaparezca del todo.

Si el proyecto no tenía id de Drive en CLAUDE.md, no hay carpeta.

4 · Claude y el PC

En claude.ai/code, las sesiones del proyecto siguen en la lista: archívalas (icono de archivo al pasar el cursor) o bórralas desde el menú de la sesión. Si el proyecto tenía un proyecto de Cowork asociado, bórralo también.

En el PC, si lo habías aterrizado: borra la carpeta C - Desarrollo\MiProyecto entera. No hay nada allí que no estuviera en GitHub.

Reglas

Las que no se negocian

  • El repo es la única fuente de verdad, para el código y para la documentación (docs/planificacion/). Todo cambio termina en main.
  • La copia del PC es de solo lectura. No se edita ahí; no existe camino PC → nube. Aterrizar sobrescribe sin preguntar, y eso es lo que lo hace seguro.
  • Drive es un espejo. Solo recibe copias; nunca se borra ni se renombra nada allí; nunca se toma nada de Drive como origen.
  • No se avisa sin verificar. "Puedes probarlo" solo con el run en verde, SHA y build.
  • Los secretos no pasan por el chat. Tokens y claves van a Settings → Secrets, del repo o de la organización, nunca a una sesión ni a un fichero.
  • Lo que hay en docs/ es público. Sin claves, sin endpoints internos, sin datos reales en los mocks.
